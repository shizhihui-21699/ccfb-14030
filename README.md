# tsidec — Java 时间侧信道检测工具

对指定的静态方法自动构造"只差秘密"的两类输入，大量测量执行时间，用统计方法判断
**耗时是否随秘密变化**，并把泄漏定位到具体的字节码基本块与源码行。

面向的场景：支付系统里自己写的签名比对、令牌校验、填充检查、模幂、敏感缓冲区清零。

```
$ ./build.sh build
$ ./build.sh run --rounds 10000
$ ./build.sh test        # 统计与行为自测
```

---

## 1. 它回答什么问题

> 这个函数的执行时间/执行路径，是否依赖于一个攻击者不知道的秘密？

注意它**不**回答"泄露版比修复版快多少"——那是两段不同代码，比较没有意义。
工具对每个实现**独立地**问上面那个问题。

## 2. 为什么在这个平台上很难，以及怎么解决

Apple M4 Max / macOS 上实测到的三个硬约束（数值来自工具内置的自检与测量输出）：

| 现象 | 实测值 | 后果 | 对策 |
|---|---|---|---|
| `System.nanoTime()` 量化粒度 | **42 ns** | 单次 ~20 ns 的调用落在同一个 tick，单次测量只有 0/42/84 | 批内连续调用 K 次，把信号放大 K 倍 |
| 配对差噪声（同函数 vs 自身） | sd ≈ 0.05–0.5 ns/次 | 纳秒级泄漏会被淹没 | ABBA 交替 + 配对差 + 截尾稳健估计 |
| 零点偏置（真值为 0 时） | ~0.001 ns（好的时候）… 0.4 ns（K 太小时） | 会把亚皮秒级噪声判成泄漏 | 自检 + 每目标零点对照 + 最小效应量门槛 |

关键数字：K=4096 时，配对差的**标准误约 0.001 ns/次**；一条依赖 ALU 指令的差异
约 0.25 ns/次，能被 t>200 地检出。这不是靠"多测几次"，而是靠**把噪声的公共分量
在配对差里减掉**。

### 测量协议

```
每轮：  [ A 批 K 次 ]  [ B 批 K 次 ]         (偶数轮先 A 后 B)
        [ B 批 K 次 ]  [ A 批 K 次 ]         (奇数轮先 B 后 A)
        配对差 d = (B批 - A批) / K
```

- **ABBA**：频率调节、缓存变暖、后台负载都是缓慢变化的公共分量，在轮流交替中相减抵消。
- **批内 K 次**：对抗 42 ns 的时钟粒度。
- **K 自适应**：按两批中**较慢**的那批反推，使批次落在 ~200 μs。慢函数（模幂 5 μs/次）
  不会把 K 撑爆，快函数（4 ns/次）不会把批次压到量化误差里。
- **截尾**：去掉偏离中位数最远的 10% 轮次，压住 GC/抢占长尾。

### 判定要同时满足四件事

1. **统计显著**：截尾 t 检验 p<1e-6 **且** 配对符号翻转检验 p<1e-3（双保险）。
2. **效应量足够大**：扣掉偏置后 > `max(3 条 ALU 指令的等效时间, 5 个标准误)`。
3. **稳定**：两半独立估计不异号。
4. **测量质量合格**：无显著漂移、较短批次 > 8 μs、自检通过。

只看 p 值会把 0.004 ns 的噪声判成泄漏；只看效应量会漏掉小而稳定的泄漏。必须两者都有。

## 3. 两条独立的证据链

工具不把一切都押在时间上。

**证据 A：插桩计数（确定性、零噪声）**
用 ASM 在每个基本块入口插入计数器，分别用两类秘密各跑 N 次，比较每块的执行次数。
- 执行了多少条字节码是**完全确定的**，不受 GC/调度/频率影响。
- 因此它能在时间差异只有几纳秒、甚至被噪声完全淹没时，仍然给出明确的结构性证据，
  并精确定位到源码行。
- 实测：`unsafeEquals` 首字节失败 21 条指令，末字节失败 525 条；第 24 行的比较块
  执行 1 次 vs 64 次。

**证据 B：配对耗时**
- 定量回答"差异有多大、要多努力才能利用"。
- 能发现**控制流完全一致但指令延迟不同**的泄漏（见下文的 `%` 例子）。

### 结论等级

| 结论 | 含义 |
|---|---|
| `LEAK_CONFIRMED` | 时间与结构双重证据 |
| `LEAK_STRUCTURAL` | 结构证据明确，时间差可能被噪声淹没 |
| `LEAK_TIMING_ONLY` | 仅时间证据。**不是误报**：典型于数据依赖/变延迟指令，需人工确认 |
| `NO_LEAK` | 两条证据都不显著 |
| `INCONCLUSIVE` | 测量质量不达标。工具拒绝在这种情况给结论 |

## 4. 示例代码与预期结论

`src/main/java/tsidec/pairs/`，每类都有泄露版与修复版：

| 类别 | 泄露版 | 修复版 | 说明 |
|---|---|---|---|
| MAC/签名比对 | 首字节即返回 | 恒定时间比较 | 最经典的签名比对泄漏 |
| 令牌校验 | 首字符即返回 | 恒定时间 | 含"只有长度不同"的变体 |
| PKCS#7 填充 | 遇非法字节提前返回 | 固定遍历整块 | padding oracle 的时间来源 |
| 模幂 | 平方-乘 | **半修复**（阶梯+`%`）与**彻底修复** | 见下 |
| 缓冲区清零 | 按秘密长度清零 | 总清整块 | 秘密长度侧信道 |

模幂这一组特别值得看：它是"看起来修好了、其实没有"的典型。

- `unsafeModExp`：轮数随指数比特变化 → 控制流泄漏，结构+时间都抓得到。
- `ladderModExp`：**每轮恒做 2 次乘模，字节码执行路径两类完全一致**，但用 `%` 归约。
  ARM64 的 `SDIV/UDIV` 是变延迟指令，实测仍留下 **+11 ns/次** 的时间差。
  工具判 `LEAK_TIMING_ONLY` —— 这是只有时间证据能发现的泄漏，也是最容易被
  "我们已经改成阶梯算法了"这种说法掩盖的一类。
- `fullyConstantTimeModExp`：固定 62 轮移位-减法归约，全部定延迟指令。
  代价是慢约 160 倍（5.4 μs/次）。工具判 `NO_LEAK`，并**如实报告**该情形下
  置信区间宽达 ±5 ns（慢函数每批只能放几十次），而不是假装精确。

## 5. 自检：拒绝在不可信时给结论

每次运行先跑一组已知答案的对照（`selfcheck/SelfCheck`）：

```
null    A/B 逐字相同的代码，真值 0        → 必须不显著
tiny    B 多做 1 条依赖 ALU 指令 (~0.25ns) → 必须显著
small   +4 条                               → 效应量应更大
medium  +8 条                               → 效应量应更大
```

从三个非零点做**带截距的加权回归**得到"每条指令 ≈ 多少 ns"的斜率。这一步有两个作用：

1. 把最小效应量门槛换成物理单位（"约 3 条指令的差异"）。
2. 若 JIT 把校准差异优化掉了，斜率会变成 0，工具据此**报校准失效**，而不是给出假阴性。

自检不通过（零点偏置 >0.25 ns、斜率异常、无法检出 1 条指令）时，直接退出码 2，
不输出任何判定。

开发过程中自检抓到过三次真实错误，都写进了注释：
- 校准用的 A/B 写成两个不同方法 → 残留 0.032 ns 偏置。
- 把两者合并成一个带 `switch` 的方法 → 内联决策不对称，产生 1.9 ns 假信号。
- K < 4096 且输入窗口用位掩码取模 → 噪声暴涨 10 倍、偏置失稳。

## 6. 使用

```
./build.sh run [选项]

  --rounds <n>    测量轮数（默认 10000，最少 1000）
  --k <n>         每批调用次数（省略 = 自动调优）
  --budget <s>    单目标时间预算秒（默认 6；慢函数自动减轮）
  --warmup <n>    预热轮数
  --json <path>   输出机器可读报告
  --only <prefix> 按类名前缀筛选，逗号分隔
```

退出码：`0` 结论与预期一致；`1` 有误判；`2` 自检未通过。

### 检测你自己的代码

1. 写一个 `Target`（见 `core/Target.java`）：给出类名、方法名、参数类型，以及
   `argsFor(secretClass, i)` —— **两类输入只许秘密部分不同，公开部分逐位相同**。
2. 把类的 `.class` 放进 `--classes` 指向的目录（默认 `out`）。
3. 加进 `cli/Main.selectTargets()`，或仿照它写自己的入口。

`Target` 的关键约束是第 1 条：如果两类输入的公开部分不同，测到的是"输入不同"，
不是"秘密不同"——这是时间侧信道检测里最常见的假阳性来源。工具有 `secretDescription()`
把这层对比写进报告，强制你把它想清楚。

## 7. 代码结构

```
src/main/java/tsidec/
  stats/        t 分布、符号翻转置换、Spearman 趋势、Holm 校正、Wilson 区间
  core/         Target / 测量引擎（ABBA、自适应 K、预算）/ 判定 / 插桩驱动
  instrument/   ASM 基本块插桩、计数器、静态分析
  selfcheck/    盲自检与校准
  pairs/        示例泄露/修复代码与目标定义
  report/       文本与 JSON 报告
  cli/          命令行
src/test/java/tsidec/selftest/   统计单元测试 + 端到端行为回归 + 重复性验收
```

`Repeatability` 是长跑验收（默认 3 轮 × 8 目标）：统计修复版的误报率与泄露版的漏报率，
只有 0 误报、0 漏报、0 无法判定才算通过。它是长跑，故不放进默认自测：

```
java -cp out:out-test tsidec.selftest.Repeatability 3 2500
```

ASM 9.9.1 以 jar 形式放在 `lib/`，不依赖网络或包管理器。

## 8. 已知局限

- **单线程测量**。多线程下计数器和计时都会被干扰；要支持并发探测需按线程隔离计数器。
- **只支持静态方法、返回 int/boolean/long**。实例方法与对象状态需要扩展 `TargetBinder`。
- **缓存侧信道只能间接发现**。基于内存访问地址的泄漏（如 AES 查表）在本工具里表现为
  `LEAK_TIMING_ONLY` 或 `LEAK_STRUCTURAL`，需要人工复核；本工具不做 cache line 级追踪。
- **慢函数分辨力下降**。每批只能放几十次时，±5 ns 的置信区间可能盖住小泄漏；
  报告会如实给出该区间，不掩盖。
- **平台相关**。所有阈值都在 Apple M4 Max / OpenJDK 27 上标定；换平台应重跑自检，
  必要时调整 `minEffectThreshold` 与批次时长。
